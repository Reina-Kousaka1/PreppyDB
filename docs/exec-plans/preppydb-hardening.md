### User-prioritized hardening order (2026-11-05)

1. WAL/file corruption and recovery.
2. Crash recovery and manifest publication.
3. Sync/commit failure semantics.
4. Restore safety and the remaining findings.

The current turn found that recovery checked sequence continuity only when the manifest
was missing. A checksum-valid record gap after a published snapshot could therefore be
accepted. Recovery now enforces a contiguous post-snapshot sequence, rejects a torn
segment followed by later segments, and explicit writable repair truncates at the first
bad frame and removes later segments before reopening the WAL. Added regressions cover a
complete terminal bad-CRC frame followed by repair/reopen, and a missing post-checkpoint
segment followed by strict rejection, suffix repair, a new write, and reopen. Focused
tests passed; all 86 storage unit tests and 32 storage integration tests passed, with the
existing child-process helper ignored by the normal harness and explicitly spawned by
its parent crash test. Storage Clippy, workspace formatting, and `git diff --check` passed.
This only advances the first workstream; crash/fault qualification and platform CI remain
open. No commit or push was made.

The next recovery pass added manifest snapshot-reference validation before any snapshot
path is opened: the filename must be the exact generation-derived name, the manifest and
reference generations must agree, sequence watermarks must be ordered, and snapshot
header/document-count/recorded-length metadata must match. Symlink snapshots fail closed
on Unix; `verify` applies the same path and metadata checks without opening an invalid
path. Regressions cover traversal, symlink, mismatched metadata, orphan snapshot plus
partial temporary manifest, and publication-before-WAL-retirement. The full storage
suite now passes with 86 unit tests and 37 integration tests (one helper is intentionally
ignored and spawned by its parent crash test).

WAL append errors now use machine-readable `commit_outcome_unknown`, since a complete
frame can be present even if a later sync call reports failure. The engine rolls back
the in-memory mutation and rejects further document reads/writes until reopen, preventing
the live process from serving a stale pre-commit view. Recovery decides the visible state;
the client must inspect it before retrying. This does not create a power-loss guarantee.
The injected partial-write/pre-sync test and workspace check pass locally. Windows
manifest replacement semantics and directory durability are still not qualified.

## Tasks and status

- [ ] **Commit atomicity and performance:** put/delete, document transactions, ordinary document batches and checked batches use targeted document undo. Schema batches and `Store::apply` batch replay use a reversible per-operation journal: prior documents are retained for rollback; created collections/indexes are removed on rollback; dropped collections/indexes are moved into the journal and restored by ownership. This avoids cloning complete touched collections. Retained prior-document JSON in live batches is capped at 32 MiB per batch, with checked accounting and an overflow regression; recovery replay is not subjected to this new live-operation cap, preserving replay compatibility for existing WAL records. A new recovery regression first reproduced a rollback failure when replay ignored a document operation for a missing collection, then verified that the undo journal now records no inverse for that no-op. Nested batches are rejected before publication because the existing WAL decoder rejects nested batch frames; a close/reopen regression covers this. Creating an index still scans/builds O(collection size). A no-dependency release benchmark overwrites one document at 1k/10k/50k document counts (101 samples each, `sync_mode=never`); two WSL2 x86_64 runs measured medians 2.146/2.522/2.579 µs and 2.141/2.566/2.615 µs, with p95 2.339/3.624/2.764 µs and 2.282/2.805/2.876 µs respectively. This is a local smoke result, not a portable claim; sync and varied transaction workloads remain unqualified. Storage validation passes (85 unit tests, 30 integration passed, 1 existing child helper ignored and explicitly spawned by its parent); full feature-enabled Linux workspace validation passes (249 passed, 0 failed, 1 ignored helper), including format, check, strict Clippy and release build. A failed sync can still have an indeterminate durable outcome, as recorded below.
- [ ] **Transaction limits:** delete previously bypassed `max_txn_writes`; it now enforces the same limit as put before recording a read. The mixed put/delete boundary test and Storage Clippy pass under Ubuntu WSL. Read sets are now capped at max_batch_ops; transaction write staging is capped at 32 MiB and committed JSON values are moved into the WAL operation list rather than cloned. Five focused tests cover read-count limits, byte-limit replacement accounting, escaped JSON output bounds, expiry preservation and rollback reuse. A two-thread barrier test repeatedly has concurrent transactions read and stage conflicting SETs; exactly one commits and the other receives TransactionConflict (run separately and included in the final suite). Storage tests pass (81 unit, 30 integration, 1 existing helper ignored); full Linux workspace validation passes (239 passed, 0 failed, 1 ignored), as do format, check, strict Clippy, release build and diff check. The staged-size check uses a bounded formatter and stops at the remaining budget instead of allocating a full temporary JSON string. Focused transaction tests and Storage Clippy passed after that change. Full Linux workspace validation passed again (239 passed, 0 failed, 1 existing ignored helper); full ARM64/QEMU storage tests passed after the escaped-JSON bound test (111 passed, 1 ignored), and Windows-GNU workspace check/strict Clippy passed. Full ARM64 workspace passed immediately before this bounded-formatter-only change; current ARM64 validation covers the affected storage crate. None of this substitutes for Windows MSVC/runtime or Docker qualification. Schema rollback no longer clones entire collections; per-batch old-document undo is capped at 32 MiB. Representative performance qualification remains open.
- [ ] **Index mutation invariants:** review of the write path found two additional concrete defects: a non-sparse missing field was inserted under null but never removed, and an error in a later unique index could leave an entry in an earlier index. Index removal now uses the same missing/null semantics and all index constraints are checked before insertion. Two regression tests and all 13 Store tests passed with Storage Clippy on Ubuntu WSL; add reopen/differential and Windows qualification.
- Transaction undo now also has a focused Unique-Index conflict test: an earlier changed document and its index entry are restored, the failed insert is absent, and the same state survives reopen. The test passed on Ubuntu WSL; concurrent and Windows cases remain.
- [ ] **Windows manifest and recovery:** removed remove-then-rename fallback. Rust documents `std::fs::rename` as replacement on Windows 10 1607+ when the filesystem supports `FileRenameInfoEx`, with different behavior on older/unsupported filesystems; do not generalize that conditional behavior into universal atomicity. A failed rename preserves the old target in Linux tests. Manifest changes are staged, and a failed publication poisons the engine; a forced temp-file creation failure preserves a prior checkpoint and passes reopen on Ubuntu. Missing manifest now also fails closed when the earliest WAL segment shows a retired prefix, and recovery without a manifest requires sequence continuity from 1. The targeted regression and normal reopen tests pass on Linux. Windows runtime/fault-injection tests, directory durability and post-rename sync failures remain unqualified.
- Manifest format parsing no longer casts an arbitrary `u64` version to `u32` with wraparound; values such as `2^32 + 1` could otherwise masquerade as supported V1. The overflow regression, all manifest tests and Storage Clippy pass on Ubuntu WSL. Windows/recovery qualification remains as above.
- Manifest reads are now capped at 8 MiB before UTF-8/JSON parsing; oversized sparse-file rejection and all manifest tests pass. This aligns the read bound with the JSON parser's maximum input and avoids allocating arbitrarily large malformed metadata.
- [ ] **WAL corruption:** complete strict terminal CRC, truncation and multi-segment recovery tests including checkpoint boundaries. A complete bad CRC is currently classified as corruption; focused Linux tests passed.
- [ ] **WAL memory bounds:** production recovery/verify and `preppydb wal` use streaming visitors; `summarize_segment` retains only count, first/last sequence and scan status. The collecting compatibility API now rejects segments over 128 MiB before allocation and directs callers to the streaming APIs; a sparse oversized-file regression and Storage Clippy pass on Ubuntu WSL. Each streaming scan still buffers one frame up to the existing 64 MiB frame bound. Full workspace tests, strict Clippy and release build have since passed on Linux; allocation amplification and platform-specific qualification remain open.
- [ ] **Backup/restore:** backup holds the state read lock during WAL sync, hashing, copying and temporary-archive verification. `backup-verify` streams archive/member hashes, extracts to an exclusive temporary directory and strictly opens/verifies the embedded database; restore rechecks copied member hashes and verifies its staged database before publication. Staging is removed on failure. A regression mutates snapshot bytes then reseals both member and archive hashes: archive-only verification used to accept the malformed database; database verification and forced restore now reject it while preserving the existing target. The test also confirms staging cleanup. Backup concurrent-write, roundtrip and semantic corruption tests pass; storage Clippy and full workspace validation pass (252 passed, 0 failed, one child helper ignored/spawned by parent). Collision, symlink, changed-byte, semantically corrupt but correctly resealed archive, backup roundtrip and force-restore tests pass. Windows reparse-point behavior and publication qualification remain open.

Manifestless pre-checkpoint archives with WAL remain supported and are validated by strict engine open, including sequence-continuity rules. The focused backup tests and integration roundtrip pass locally.

## Decisions and open risks

- Preserve the current WAL/disk format unless an explicit, tested migration is required.
- A returned I/O error after a complete write or failed sync may have an indeterminate durable outcome. Tests and public semantics must distinguish this from definite abort; do not promise that all failed commits disappear after recovery.
- Full-store staging and touched-collection cloning have been removed from the schema batch rollback path. Schema-batch undo now moves dropped collections/indexes and retains only touched prior documents, with a 32 MiB serialized prior-document cap. Ordinary document transaction undo retains prior values and transaction staging has its separate documented limits. No representative large-store benchmark exists; index creation remains O(collection size). A failed sync can still have an indeterminate durable outcome.
- The original Windows remove-then-rename fallback was unsafe and has been removed. Do not claim that rename and directory durability are crash-safe on every Windows filesystem without platform-specific qualification.
- A manifest referencing a missing snapshot fails closed. A missing manifest also fails closed when snapshot files or retired WAL history are present, and manifestless WAL recovery requires contiguous sequence numbers starting at 1. `missing_published_snapshot_fails_closed_after_checkpoint` passed under Ubuntu WSL; Windows publication and fallback remain open.
- Do not claim completion from green tests alone. PR remains blocked until every merge-blocking issue and cross-platform acceptance gate has evidence.
